# 32格方块棋子制作与逐链验收计划

## 目标与当前状态

以用户确认的32格方块风格制作棋子；统一在9列×6行、斜45°的棋盘中检验。每次只制作一条完整合成链，交付可查看的结果，用户确认后才开始下一条。

当前：序号1～23已获用户确认；按用户要求连续制作第24～30条，共44个模型，待集中验收。未修改正式游戏配置，也未部署正式素材。序号31及以后未开始。

## 数量核对

数据来源：通过 scripts/model-catalog.cjs 读取运行时 getAllProps()（含TypeScript追加配置），核对 PropConfig.ts 和 prop_prop.json。

- 当前有463条道具记录，不等于463件都需要独立模型。
- type 1～7 中有68个 type:typeson 分组，其中62个包含多件道具，6个为单级分组。
- 全表按 blessId 合成关系查到66个无前驱的合成起点；这是另一个口径，包含主分类外的资源/奖励等。
- 用户提出的63条作为原始项目目标保留，但当前配置未核实为63。不可为了凑数删除分组。下方列出全部68个主分类分组作为制作台账。
- 每条开工前沿 blessId 核对实际顺序、满级、分支和异常引用；不能靠ID连续或luna排序猜测。主分类外的金币、钻石、体力、手提包等另行列入补充批次，不混入63条口径。

## 固定美术与交付规格

1. 方块基准为每个标准格宽32个体素，棋子最大占地约0.83格。细小零件不必占满格；保持把手等共享部件尺度一致。
2. 轮廓简洁，木材蜂蜜橙、接缝深棕、铁皮灰蓝作为基础色系；优先通过轮廓与结构区分等级，允许为等级辨识调整主色与辅色，不要求全链同材质始终同色。
3. 不做凸起线圈木纹、随机碎细节和均匀满屏噪点。圆形改为阶梯轮廓；像素色块只在必要位置使用。
4. 无投影，沿用同一灯光；确认正面、背面和斜45°效果。
5. 输出GLB和可编辑Blender源文件；剔除内部面、合并网格、复用材质，不能每个体素保留为独立运行时对象。
6. GLB为Y-up、底部居中的原点、根节点单位变换。模型单独导出，不能混入其他场景、相机或灯光。
7. 棋盘Demo当前棋子显示比例0.76；制作按原始模型尺度，缩放由展示统一处理，不重复烘焙。
8. 导出基础色与粗糙度材质，不能只设置Blender视口颜色；在网页加载真实GLB后验收。
9. 单链预览包含全部等级、名称和ID、64/96像素小图、旋转与下载；另提供棋盘内拖动、合成、重置测试。
10. 源文件保留已通过版本；试验模型与生产配置分开，预览不等于正式替换。
11. 等级辨识度为强制验收项：每一级都要与相邻等级明显区分，并检查全链混排时是否容易混淆。优先改变轮廓、体积比例、层数或主要功能结构；结构差异不足时，必须补充清晰的主色或大面积辅色变化（如箱体、箱盖、框架），不能仅靠小铆钉、细线、微弱色差或等级文字。配色保持同一美术风格与材质逻辑，不强制套用白绿蓝紫等品质色序列。在64/96像素预览和斜45°棋盘实际显示比例下，隐藏名称及等级标签检查，确认升级变化仍可辨认。此规则也适用于当前待验收的维修工具箱链，不只用于后续链。

## 每条链的流程与停止点

1. 核对：读取实际ID、名称、blessId、发射器/产出关系、原图，明确完整等级。
2. 设计：列出各等级可见新增结构、主色/辅色，以及与前一级的主要辨识差异；名称与原图冲突时在交付表中列出现有名称及建议名称，不直接篡改游戏数据。
3. 制作：只做当前链；保留已认可的共同造型，再增加等级差异。
4. 自检：查看实际网页截图与多个角度；检查材质、穿插、悬空、轮廓。逐对比较相邻等级，再检查全链混排；在64/96像素和实际棋盘中隐藏名称/等级检查辨识度。仍易混淆的等级先调整结构，必要时增加主色/大面积辅色差异，再交付。
5. 验证：检查GLB有效性、尺寸、原点、资源加载、移动端溢出、拖动/合成，以及最高级不可继续合成。
6. 交付：发出当前完整链预览链接、棋盘链接、GLB/源文件位置及简短变更说明。状态标记为“待用户验收”。
7. 等待用户确认：有反馈则只修当前链。用户明确通过后记录结果，再进入下一条；不并行批量制造尚未批准的链，也不自动部署。
